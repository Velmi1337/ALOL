# Совместимость

## Proton и Wine

Основной вариант ALOL — GE-Proton через UMU. UMU обеспечивает запуск Proton
в Steam Linux Runtime вне Steam и загружает необходимые компоненты.
ALOL использует `umu-run`, а не запускает внутренний `files/bin/wine`
из сборки Proton напрямую.

- [GE-Proton](https://github.com/GloriousEggroll/proton-ge-custom)
- [UMU](https://github.com/Open-Wine-Components/umu-launcher)
- [UMU FAQ](https://github.com/Open-Wine-Components/umu-launcher/wiki/Frequently-asked-questions-%28FAQ%29)

Нет сравнительных тестов, подтверждающих единственную лучшую сборку для Arizona.
Рабочая версия зависит от клиента игры, драйверов и оборудования. После успешной
подготовки ALOL закрепляет использованную сборку по данным префикса.
Можно выбрать другую установленную сборку или абсолютный путь к Proton.
Системный Wine использует отдельный префикс.

Для Proton/DXVK нужны подходящие 32- и 64-битные драйверы Vulkan.
При проблемах с Direct3D попробуйте WineD3D/OpenGL. При пустом окне официального
лаунчера включите отключение его GPU. Для Electron используется `--no-sandbox`,
поскольку Windows sandbox Chromium не поддерживается Wine.

## Подготовка и запуск

ALOL создаёт префикс явным вызовом `C:\windows\system32\wineboot.exe -u`.
Команда UMU `createprefix` не используется: в исследованной версии она создавала
окружение, но затем пыталась запустить пустой EXE и возвращала ошибку ShellExecuteEx.

Прямой запуск воспроизводит параметры игрового EXE из исследованного официального
лаунчера Arizona: адрес, порт, ник, память, графические настройки, параметры модов
и существующий служебный идентификатор. Идентификатор не генерируется заново
и скрывается при печати команды. Для обновления файлов используется отдельный
запуск официального лаунчера.

Публичные форматы каталога и манифестов модов также проверены по официальному
клиенту. Копий его JavaScript-кода и игровых ресурсов в исходниках ALOL нет.
Изменение API или клиента Arizona может потребовать обновления адаптера ALOL.

## Известные проблемы

Знаки вопроса вместо русского текста могут быть связаны с ANSI 1252 в префиксе.
ALOL задаёт `ru-RU`, ANSI 1251, OEM 866 и `LANG`/`LC_ALL=ru_RU.UTF-8` для дочерних
процессов. В Linux должна присутствовать локаль `ru_RU.UTF-8`.
Язык рабочего стола не меняется. Описание проблемы:
[база знаний Arizona](https://chatwoot.arizona-rp.com/hc/arizona-rp/articles/1738955157-).

Ошибки `Failed to load font file ...:Zone.Identifier` возникают, когда Windows-метки
попадают на Linux в виде отдельных файлов. ALOL переносит только распознанные
метки `[ZoneTransfer]`/`ZoneId` в резервную папку, сохраняя настоящие шрифты и DLL.

## Пределы проверки

Модульные и интеграционные тесты проверяют параметры запуска, сохранение профилей,
блокировку префикса, установку и откат модов, обработку архивов, кодировки и ошибки.
В интеграционных тестах Wine/UMU и HTTP-загрузки заменены фикстурами.

Среда разработки не предоставляет доступ к графической сессии и сетевым сокетам
Windows-runtime. Полный вход на сервер, античит, FPS, звук и длительная стабильность
не покрыты этими тестами. Их проверяют обычным запуском ALOL в графической сессии
на целевой машине. Совместимость со всеми серверами и сборками Wine не гарантируется.
